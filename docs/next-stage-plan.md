# DevFlow 下一阶段计划：本地运行、报告质量与可恢复协作

规划日期：2026-11-10；本轮范围于2026-11-11调整为本地运行和真实评测闭环，发布封装取消。任务3的报告格式与检查已完成；任务4于2026-11-12完成本地实现和20题真实对照验收，见[复核前后对照](report-review-baseline.md)。任务5及以后仍为后续备选。
定位：在已有 PR/CI、RAG、记忆审核和恢复能力上，建立可验证的分析质量，再扩展受控的专业 Agent 协作。
初版仅制定计划；任务1/2现已获授权实施，当前证据见[核对表](release-checklist.md)。既有 GitHub 只读范围继续适用；真实写操作需要另行确定范围。

## 二、当前目标：本地运行与真实质量基线

### 任务1：核对原第22—24步，完善本地运行与验证

- 逐项登记已验收、已有实现但缺记录、尚未实现，附代码/测试/运行证据；原发布事项注明本轮不实施。
- 本地API、worker、前端和PostgreSQL/pgvector按手册可启动并检查就绪，提供排障方法。
- 迁移只有bootstrap显式入口；依赖和权重仅在安装/显式准备阶段下载。
- 无真实费用的本地统一检查包含静态、契约、前端构建、隔离数据库和故障恢复测试。
- 用隔离测试库与制品目录验证源码服务启动、重启、fixture演示和报告/文档/记忆持久性。
- 保留未提交工作及既有Compose/CI文件；不继续发布封装、候选版本、镜像分发和跨机器验收。

产物：[核对表](release-checklist.md)、[本地启动与排障手册](local-runbook.md)、检查命令、演示流程及[验证记录](local-verification-20261111.md)。
验收：当前电脑可运行fixture；真实模式仅需服务端凭据；重启不丢数据；工程检查不消耗真实额度。

### 任务2：真实模型和生产检索分层基线，完成评测闭环

- 保留fake工程回归，不扩展规则识别器代替真实模型。
- 当前配置的供应商/模型/报价执行固定输入，保存配置、输出、实际读取、usage和来源哈希。
- 开发集评测、GPT语义复核、失败定位、改进回归后冻结；再创建并执行新留出集。原已查看留出只作回归。
- 生产检索适配器使用隔离PostgreSQL/pgvector和同一固定文档语料，不改日常知识库。
- 受控对照关键词与混合检索、未压缩与预算压缩，记录不相关配置保持一致的证据。
- GPT逐题对照原始输入、实际工具读取和结论，记录判定、理由、证据位置及失败归因，明确复核者为GPT。
- 分开报告Recall@6、引用有效性与语义支持、PR误报/漏报、CI根因/不确定性，以及耗时、token和费用。
- 固定3题各重复3次，保存逐次结果并说明波动，不将一次结果当稳定成功率。
- 真实调用沿用200元共享账本和180元停止线，先看余额、分批执行，不重置或提高预算；未知用量保留预留。

产物：真实分析/检索基线、两组实验报告、GPT复核记录、失败归因和前后回归记录。
验收：每个结论可追溯输入/证据/费用，区分模型、检索、工具读取和评分规则造成的失败；fake零token不描述真实成本。

## 三、第二优先级：提高报告可信度（约1周）

### 任务3：把报告分成事实、推测和建议

实现说明见[报告怎么写，结论怎么核对](report-rules.md)，检查结果和仍需修改的模型结论见[验证记录](report-v2-verification-20261111.md)。

- 为发现增加结论性质、直接证据、必要前提、未确认条件与严重程度依据。
- 采集完整性、日志截断、当前提交和知识库是否启用等事实，从可信工具元数据获取。
- 只有读取范围不足或采集明确截断时才能声明截断；没有调用链不能断言系统级可达性。
- 历史案例只能作为检索线索；没有当前版本证据时，不能计为当前缺陷。
- 按共同根因合并风险，保留不同后果与证据；建议项不计为新增缺陷。
- 保持旧报告可读，为新报告增加版本标识；无法从旧材料确定的新字段显示未知，不事后伪造。

产物：新版报告契约、证据边界规则和前端分类展示。
验收：历史已发现的四类语义问题均有回归用例；引用存在校验与语义支持判断分别记录。

### 任务4：增加有限的报告复核与补查

- 先执行确定性检查：引用身份、版本、实际已读范围、截断和元数据一致性。
- 对高风险或有明显证据缺口的发现，调用一次有明确判断规则的复核步骤。
- 复核仅输出：可保留、需补证据、应降为假设、应删除；附证据原因，不接受无依据的自我打分。
- 有预算时最多补查一轮；预算不足则保留缺口，不能无限反思或反复重试。
- 模型复核是辅助判断，不给报告贴自动认证正确的标签；关键案例由GPT按用户要求对照原文复核，复核者如实记录为GPT。
- 新输出绑定新哈希，不能继承旧输出的语义复核通过状态。

产物：失败分类、复核记录、补查轨迹和基线对照。
验收：开发集中的目标错误减少，已通过回归不出现未解释退步；同时报告拒答增加、耗时和费用变化。

## 四、第三优先级：按问题检索长期记忆（约1周）

### 任务5：升级记忆召回

- 在人工审核、仓库、有效期和版本过滤之后，再进行向量与关键词检索，返回最多6条相关经验。
- 记忆向量保存模型与内容版本，摘要编辑后需要重新索引并重新审核。
- 召回时展示来源、匹配原因和适用条件；没有足够相关经验时不强行填满6条。
- 新经验与旧经验存在冲突时进入候选审核，展示差异，不能自动覆盖。
- 记忆仍不能替代当前代码事实；旧错误报告提取的经验必须可追溯撤销。

产物：语义记忆检索、索引状态、命中说明和冲突审核视图。
验收：准备至少30条同仓库经验，验证相关但较早批准的条目可召回；撤销、过期、版本错配及跨仓库隔离仍成立。

### 任务6：做记忆效果对照

- 在相同模型、数据和预算下比较：不使用记忆、最近6条、语义检索记忆。
- 测量相关经验召回、错误经验干扰、输入token和答案质量。
- 保留错误与冲突记忆的负面案例；只在实验支持时对默认行为做变更。

产物：记忆对照报告和默认策略说明。
验收：能说明语义召回在什么任务有效、何时没有收益，而不是仅证明多了向量字段。

## 五、第四优先级：可恢复的专业 Agent 协作（约1—2周）

### 任务7：先做固定协作流程

新增场景：“综合 PR 改动和 CI，判断还缺哪些合入条件。”

流程：确定任务范围 → PR分析与CI分析并行 → 检查证据缺口和冲突 → 汇总带条件的建议。

- 使用固定图和代码路由选择任务，不先让模型生成任意DAG。
- PR与CI使用独立提示词、输入范围和结构化输出，共用可信证据目录。
- 子任务限定到同一PR提交；找不到对应提交的CI时显示缺失，不用默认分支最新CI代替。
- 子任务保存独立状态、输入、结果和checkpoint命名空间，由父任务统一管理取消、截止时间和预算。
- 默认只并行两个专业任务；未使用的分支可跳过，失败时区分部分完成与全部完成。
- 不复制父任务整份预算给每个子任务；并发调用在同一个费用账本预留，取消后不启动新分支。
- 增加内部workflow并发配额；默认普通任务原有上限不变，复用6次模型和12次工具总限额的首版配置，超过则明确返回缺口。

产物：固定协作图、父子任务记录、共享预算和取消逻辑。
验收：能演示一个分支失败、进程重启、旧worker提交被拒、并发预算不足和部分结果汇总。

### 任务8：增加工作流前端和对照实验

- 展示节点状态、依赖、每个专业任务的证据、失败原因和累计成本。
- 允许展开专业结论，汇总时不得抹掉少数分支的风险或不确定性。
- 使用同一复合任务集比较单Agent和固定协作，分别报告相同预算与自然成本下的结果。
- 协作确有收益后，再考虑独立的Planner、有限重规划和Issue专业任务；没有收益时保留简单路径。

产物：工作流工作台、单Agent与协作对照、设计取舍文档。
验收：前端体现真实调度与恢复状态；不以Agent数量作为效果指标。

## 六、最后安排与停止条件

建议顺序：发布检查与真实基线 → 报告质量 → 记忆语义检索 → 固定协作。约4—5周，具体取决于评测标注和已完成的发布项。

如近期要投递，完成前两阶段即可冻结求职版本，同时展示现有RAG、恢复和记忆；后两阶段可以继续迭代，不以全部扩展完成作为投递前提。

本轮不排入：真实GitHub写操作、自动合并、修改代码、执行第三方仓库、公开多租户平台、Kubernetes、额外消息系统，以及单纯为技术栈数量替换向量数据库。

每阶段结束保存可复现版本、测试与评测结果、失败案例和三分钟演示。所有新增文本按CRLF保存。
